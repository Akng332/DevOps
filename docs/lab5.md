# ЛР 5. Continuous Integration

CI выполняется в GitHub Actions (`.github/workflows/ci.yml`) при push, pull request и ручном запуске. Ветви `main`, `lab5/**` и `lab6/**` охвачены правилами push. Pull request проверяется до слияния.

## Барьеры проверки

1. **Format and tests**: закреплённый .NET SDK 10.0.404, восстановление зависимостей по lock-файлам, `make format`, `make test` с порогом покрытия 40%. Кэш NuGet ускоряет повторные прогоны. Лог тестов и Cobertura сохраняются как артефакт.
2. **Disposable PostgreSQL migration and restore**: отдельный PostgreSQL 17 в контейнере CI. Сценарий `make db-check` проверяет начальную схему, миграции на базе с данными, повторный запуск и восстановление после намеренного изменения. Рабочая база не используется.
3. **SAST, secrets and dependencies**: `make sast` с закреплённым Semgrep; Trivy проверяет исходники на секреты и уязвимые зависимости. Находки высокого и критического уровня останавливают job. Отчёты сохраняются даже после ошибки.
4. **Container environment and image scan**: тот же `make container-check`, который применялся в ЛР 4, проверяет Docker Compose, здоровье API и БД, сохранение записи, backup/restore и остановку. Образ дополнительно проверяется Trivy.
5. **Publish image after all gates**: выполняется только после успеха всех обязательных jobs и только на push. Образ отправляется в GitHub Container Registry с неизменяемым тегом `sha-<полный SHA коммита>`. Для pull request публикация отключена. `GITHUB_TOKEN` получает право `packages: write` только в job публикации.

## Защита критических файлов

`.github/CODEOWNERS` помечает тесты, Makefile, конфигурацию CI, Semgrep и сценарии проверки. Для фактической защиты на целевой ветке GitHub нужно включить правило: обязательные статусы четырёх проверочных jobs, запрет обхода для участников с правом записи и **Require review from Code Owners**. Сам файл CODEOWNERS не может принудить ревью без такого правила. Одобрение собственного изменения автором не считается независимой проверкой; для защиты потребуется второй участник с правом ревью.

Для демонстрации ошибки можно создать отдельную учебную ветку с намеренным нарушением теста или добавить тестовый секрет, открыть PR и показать, что требуемая проверка красная, а job публикации не выполняется. После демонстрации дефектную ветку не сливать.

## Проверка

Локально доступны прежние команды `make format`, `make test`, `make sast`, `make db-check`, `make container-check`. На Windows текущей машины нет .NET SDK 10 и Docker CLI, поэтому серверный прогон следует оценивать по результатам GitHub Actions и при необходимости повторять на Debian ВМ.
